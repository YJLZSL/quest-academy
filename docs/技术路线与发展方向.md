## 一、当前阶段的真实定位

### 1.1 一句话判断

> **这是一个"完成度很高、但没跑起来"的项目。**

代码结构工整、分层清晰、文档齐备，但实际交付能力存在三个断层：**构建断层、质量断层、价值断层**。

### 1.2 项目资产盘点（实测数据）

| 维度 | 数值 | 评价 |
|------|------|------|
| Dart 文件 | 119 个 | 规模适中 |
| 代码行数 | 约 31,000 行（不含生成代码） | 中等体量 |
| 测试文件 | 32 个 | 覆盖尚可 |
| 测试用例 | 481 个（`test(` 计数） | 数量可观 |
| 数据表 | 11 张（schemaVersion 3） | 设计完整 |

| 文档 | README + AGENTS（55KB）+ 架构设计 + 代码百科 + CHANGELOG | **异常完备** |

### 1.3 三个断层

#### 断层 1：构建断层 —— **已于 2026-08-28 修复**

安卓端构建原为**七层阻塞叠加**（详见《诊断-安卓构建卡死.md》）：

```
L1  Gradle Wrapper 下载 250MB（~38KB/s）       → 约 1.8 小时
L2  Flutter SDK 位于 %TEMP% 且被删掉 93% 文件  → includeBuild 指向空构建
L3  maven.google.com TCP 不可达                → AGP 9.0.1 无法解析
L4  Android SDK 缺 platform-36 / build-tools   → 已由 AGP 自动补装
L5  NDK 缺失                                   → 移除 ndkVersion（原生依赖为预编译 .so）
L6  Kotlin 跨盘符崩溃（项目 D: / Pub 缓存 C:） → 缓存迁至 D:\PubCache
L7  插件 flutter_native_splash 锁 compileSdk 31 → 根 build.gradle.kts 统一为 36
```

**修复后验证结果**：

```
flutter build apk --debug                          ✅ 162.8 MB
flutter build apk --release --no-tree-shake-icons  ✅ 67.7 MB
flutter build windows --release                    ✅ quest_academy.exe
```

**唯一遗留**：Android Release 需 `--no-tree-shake-icons`（引擎产物
`const_finder.dart.snapshot` 缺失）。**把 Flutter SDK 重装到非 `%TEMP%` 路径**即可去除
该 flag，并消除 L2 复发风险——这是目前技术栈上最该做的一件事。

#### 断层 2：质量断层 —— 门禁形同虚设

```yaml
# .github/workflows/ci.yml
- name: Flutter test with coverage
  # 测试步骤设为 continue-on-error：已知有 36 个预存测试失败
  continue-on-error: true
  run: flutter test --coverage
```

- **36 个测试失败被永久跳过**，测试不再构成质量门禁
- `flutter analyze` 也被降级为"仅 error 阻塞"，info/warning 不阻塞
- 依赖状态：`1 package is discontinued. 62 packages have newer versions incompatible with dependency constraints.`
  - `flutter_markdown 0.7.7+1` **已停止维护**（官方建议迁移 `flutter_markdown_plus`）
  - `sqlite3_flutter_libs 0.5.42` 已标记 EOL
- `pubspec.yaml` 声明 Flutter 3.44.4，实际 SDK 是 3.44.9；CI 锁 3.44.4 —— 版本不一致

**影响**：无法判断新改动是否引入回归，技术债在累积但看不见。

#### 断层 3：价值断层 —— 建了但没用

实测引用关系，发现一批**已完整实现、但零业务调用**的基础设施：

| 资产 | 状态 | 排除定义/注册后的引用数 |
|------|------|------------------------|
| `SpacedRepetitionService`（SM-2 间隔重复，1/3/7/14/30 天） | 已实现 | **0**（无任何 UI 引用） |
| `ConfusionDetectionService`（困惑检测自动降级） | 已实现 | **0** |
| `LearnerProfiles` 表 + `LearnerProfileRepository` | 已建表 | **0** |

| `lib/features/achievements/` | 空目录 | — |
| `lib/features/home/empty_states/` | 空目录 | — |

**影响**：这些是"看起来很先进"的架构投资，但**没有一个产生了用户可感知的价值**。典型的基础设施先行、产品价值滞后。

## 二、当前阶段的核心目标

### 2.1 核心目标（唯一）

> **让「一个真实用户从安装到学完第一个知识点」这条主链路，在 Android 和 Windows 双端稳定跑通，并且可持续验证。**

不是"加更多功能"，不是"做更好的架构"，而是**把已有的一条链路真正跑通并守住**。

### 2.2 为什么是这个目标

当前这条主链路在**三个环节同时断裂**：

| 环节 | 状态 | 证据 |
|------|------|------|
| 能构建出可安装的包 | ❌ 断裂 | 安卓构建完全跑不通 |
| 能看到该看到的课 | ❌ 断裂 | L0 课程因 JSON 损坏静默消失 |
| 能知道用户是否真在用 | ❌ 断裂 | 零埋点，所有留存指标无法观测 |

任何新功能加在这条断裂的链路上，都是在增加不可验证的复杂度。

### 2.3 三个可衡量的阶段目标

| 目标 | 当前 | 目标值 | 意义 |
|------|------|--------|------|
| 双端构建成功率 | Android ❌ / Windows ✅ | 两端均 100% | 一切改动可验证 |
| 课程加载成功率 | 50%（1/2） | **100%** | 消除静默失败 |
| 失败测试数 | 36 | **0** | 恢复质量门禁 |

## 三、需要优先验证的关键假设

这个项目的很多设计建立在**未经检验的假设**上。按"错了会怎样"排序：

### H1（最致命）：用户愿意为了使用而自备 API Key

- **假设**：非商业化 + 用户自备 API Key 是可行的产品模式
- **现状**：引导第 2 步就是 API 说明，第 3 步强制配置 API Key，配不了就用不了
- **为什么最致命**：这是**转化漏斗最陡的一处**。用户还没体验到任何价值，就要先去注册 OpenAI/Anthropic 账号、充值、找 Key、填进来
- **如何验证**（低成本）：
  1. 埋点：引导页各步骤的到达率与流失率（当前**零埋点**）
  2. 若流失集中在 API 配置步骤 → 假设不成立，需要设计"免配置体验路径"
- **不验证的后果**：所有功能都建在用户根本走不到的后面

### H2：苏格拉底式引导比直接给答案更受用

- **假设**：产品的核心差异化（引导式提问而非直接给答案）确实是用户想要的
- **现状**：4 个 prompt 变体已就绪（`socratic_system_prompt.md`、`socratic_advanced.md`、`socratic_young_learner.md`、`direct_answer_prompt.md`），但**没有任何效果度量**
- **如何验证**：
  1. 对话后轻量反馈（👍/👎 + 可选原因）
  2. 对比：苏格拉底模式 vs 直接解答模式的使用占比与满意度
  3. `direct_answer_prompt.md` 的存在本身说明已经考虑了降级路径
- **不验证的后果**：可能花了大力气做了一件用户不买账的事

### H3：间隔重复能提升留存

- **假设**：`SpacedRepetitionService` 实现的 SM-2 变体能改善"学完就忘"
- **现状**：算法、数据表、服务全部就绪，但**零 UI 接入**，从未在真实数据上跑过
- **如何验证**：接入后埋点观测 —— 复习触发率、完成率、以及**复习用户的 7 日留存 vs 未复习用户**
- **不验证的后果**：可能投入 UI + 通知 + 调度开发，结果用户不买账

### H4：课程内容质量足以支撑学习

- **假设**：现有课程内容能让用户学得下去
- **现状**：宣称 L0–L4，实际 2 门课文件，其中 L0 还**损坏加载不出来**
- **如何验证**：先修好 L0，观测完成率与流失节点
- **不验证的后果**：内容生产是人力瓶颈，在验证内容模板前批量生产 = 高风险投入

### H5（技术侧）：依赖与工具链升级不会引发连锁反应

- **现状**：62 个包过期、1 个停用（`flutter_markdown`）、`sqlite3_flutter_libs` EOL
- **风险**：越晚升级越痛；`flutter_markdown` 停用意味着 Markdown 渲染（核心功能）未来无安全更新
- **如何验证**：单独开分支升级，跑通 analyze + test + 双端构建

## 六、技术路线总结

### 6.1 一句话路线

> **先修通路（构建 + 埋点），再补内容（L0 修复 + L2 补齐），最后接价值（复习闭环 + 对话质量）。所有"看起来很先进但未接入"的基础设施，一律等数据说话再动。**

### 6.2 决策原则（供后续判断参考）

1. **不可验证的改动不做** —— 构建跑不通前，只做不依赖真机的改动
2. **静默失败优先于新功能** —— 一个看不见的失败比一个缺失的功能危险得多
3. **有数据才调优** —— 所有"算法/推荐/个性化"类工作，等埋点有数据再启动
4. **假设先于实现** —— H1~H4 中任何一个被证伪，都应暂停对应方向的功能投入
5. **文档是资产也是负债** —— 本项目的文档异常完备（AGENTS.md 55KB），但文档里已经出现了过时信息（Temp 路径、3.44.4 版本号），需要建立"文档随代码同步"的检查习惯
